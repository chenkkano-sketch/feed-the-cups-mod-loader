# 杯杯倒满 Mod SDK 1.0

加载器 1.0.2，适配 Feed The Cups 1.0.2.0 / Godot 3.6.1。界面和运行时只需要 Windows 自带 .NET Framework，不需要安装 Python、Godot 或 .NET SDK。源码构建工具另行放在 src 中。

## 目录与分发

```
游戏目录/
  杯杯倒满Mod加载器.exe
  FTCModLoader/
    Core/                   加载器兼容层，Mod 不应修改
    Mods/作者名.模块名/
      mod.json              唯一清单，必须在 Mod 根目录
      Entry.gd              生命周期入口
      ...                   本模块脚本和素材
    Profiles/*.json         启用组合
    Cache/                  自动生成，可在退出游戏后清理
    Logs/                   启动及运行日志
    Backups/                导入更新时保留的旧模块
    SDK/                    规范、清单 Schema 和示例
```

每个 Mod 必须自包含。打包 ZIP 的根目录直接包含 mod.json，扩展名改成 `.ftcmod`，在管理器导入或拖入窗口即可安装。也可以直接把模块文件夹放进 Mods；文件夹名称必须等于 id。不要分发游戏 EXE、原版 PCK 或 Cache。关闭某个 Mod 后再启动，它的脚本与补丁不会进入新运行包。运行中的游戏不热切换模块。

Mod 是本机 GDScript 代码，能力声明用于规范和 API 检查，不构成脚本沙箱。加载器会阻止压缩包越界路径、链接、重复路径、危险 Windows 文件名和过大的包，但无法限制脚本直接调用 Godot 原生接口。

## 清单

参考 `mod.schema.json` 和 `Example/mod.json`。最小清单：

```json
{
  "schema_version": 1,
  "id": "example.hello",
  "name": "示例 Mod",
  "version": "1.0.0",
  "api_version": "1.0",
  "game_versions": ["1.0.2.0"],
  "entry": "Entry.gd",
  "capabilities": ["gameplay", "config"],
  "dependencies": {},
  "conflicts": []
}
```

ID 仅允许小写英文字母、数字及分隔符 `. _ -`，以字母开头；版本为三段整数。入口和模块内路径使用 `/`，不能使用绝对路径或 `..`。未知清单字段会报错。依赖格式为 `{ "作者.依赖": ">=1.0.0" }`；支持精确版本、`>=`、同主版本的 `^`、`*`。依赖必须同时启用；加载器按依赖和可选 load_after 排序，检查循环及 conflicts，顺序与文件系统枚举无关。

能力：`gameplay`（玩法及速度）、`input`（输入拦截）、`ui`（界面节点）、`config`（模块配置）、`save`（模块数据）、`recipes`（注册配方）、`levels`（注册关卡）。save_data 同时要求 config 和 save。

可选 save_profile 为独立存档组 ID；要求不同存档组的 Mod 不能组合。未声明时使用 `%APPDATA%/Feed The Cups Modded`。房租模块使用 `rent_mode` 特例保留已有 `%APPDATA%/Feed The Cups Rent Mode` 营业存档。房租 0.9.0 为该存档组增加同账号正常档的之家数据双向共享，具体白名单与事务规则见下文；这不是所有 Mod 存档共用的接口，其他存档组继续隔离。模块配置保存在当前存档组的 `ftc_mods/<id>/`。

## 生命周期

Entry.gd 继承 Reference，必须实现 `on_load(context)` 并在成功时返回 true；可选 `on_unload()` 在退出时调用。原版 autoload 初始化完成后，加载器才依次调用入口。不要给自己再次添加 autoload，也不要实现 SceneTree 来接管游戏启动。

```gdscript
extends Reference
var api
func on_load(context):
    api = context
    api.subscribe("day_start", self, "_day_start")
    api.log("已加载")
    return true
func _day_start(_event):
    api.log("新一天开始")
```

只有通过 api.add_root 创建的根节点、注册的输入钩子等才能由加载器按模块归属清理。on_load 失败会跳过依赖它的后续模块并记录日志；复杂资源补丁不能保证在运行时回滚，所以修改后请重新启动游戏。

## context 公共接口

| 接口 | 说明 |
|---|---|
| offline() | 当前是否单机；玩法接口在联机时停止生效 |
| player() / current_level() | 当前玩家与 Level，可能为 null |
| native_game() | 返回原版 GameLogic，兼容逃生口；其私有成员不属于稳定 API |
| config_path("settings.cfg") | 生成本模块配置路径和目录；文件名仅支持 ASCII 字母数字、点、下划线及短横线 |
| save_data(dict) / load_data(default) | 当前存档组下的模块 JSON 数据，不写其他模块目录 |
| add_root(name, node) | 挂载自有根节点；重名拒绝，必须声明 gameplay 或 ui |
| provide_service(name, object) | 导出 `id:name` 服务，不允许覆盖 |
| service(mod_id, name) | 获取其他模块服务；应在 dependencies 声明使用的模块 |
| subscribe(event, target, method) | 回调始终接收一个 Dictionary |
| publish(name, data) | 发布 `<本模块id>:<name>` 事件 |
| set_game_speed(factor) | 各模块倍率相乘，整体限制 0.1～8，全部恢复 1 时还原进入前倍率 |
| set_movement_multiplier(factor) | 基于原版计算结果相乘，不修改原版 Stat，正常移动与搬运减速都保留 |
| register_movement_provider(target, method) | 动态倍率回调接收 actor 并返回数值，例如冲刺 |
| register_control_hook(target, method, priority) | 回调 `(actor, button, value, type)`，返回 true 消费输入；高优先级先执行 |
| recipe(name) | 配方数据的深拷贝 |
| register_recipe(name, base, values) | 从已有配方派生，名称必须以 `<id>.` 开头，原配置重载后仍存在 |
| register_level(name, base, values) | 从已有关卡派生，名称必须以 `<id>.` 开头，原配置重载后仍存在 |
| add_money(amount) | 单机时通过原版资金变更接口操作资金 |
| log(message) | 写 FTCModLoader/Logs/runtime.log |

框架事件：`loader_ready`、`scene_loaded`、`day_start`、`new_day`、`store_opened`、`menu_changed`、`reward_opened`。scene_loaded 带 node、level；loader_ready 带 mods、failed。不要在每帧轮询整个场景树或重复注册钩子。使用 weakref 持有临时场景对象，退出关卡后检查有效性。

房租服务：`api.service("ftc.rent_mode", "mode")`；修改器服务：`api.service("ftc.trainer", "trainer")`。自由搬运服务：`api.service("ftc.furniture_carry", "mode")`，提供 `is_run()`、`is_preparing()`、`toggle()`、`can_open()`；后者检查手持、搬运开关及寻路更新状态，可在自定义开店按钮改变时间前调用。`api.service("ftc.furniture_carry", "carry")` 返回搬运操作对象，可在保存前 `cancel()` 归还尚未放下的设施。服务可为 null，请用可选 load_after 或 dependencies 声明顺序。目前返回现有模块实例，其内部私有方法可能随模块版本改变。

人才市场 1.1.0 服务：`api.service("ftc.talent_market", "market")`。只读查询可用 `is_run()`、`active()`、`can_manage()`、`is_modal_open()`、`daily_wage(person)`、`wage_total()`；管理入口为 `open_market()`、`close_market()`，以及仅开店前有效的 `hire(id)`、`fire(id)`、`set_duty(enabled, id)`、`refresh_candidates()`。店员统一为 `employee`，由主动技能决定工作，不再提供调岗入口。其他模块打开暂停面板前应检查 `is_modal_open()`，不要夺取输入或暂停状态。进入布置/序列化前可用 `before_layout_save(level)` 停止工作并归还持物；普通关卡扩展已接入此接口。不要直接修改员工对象、工资或存档字段。

人才市场使用普通关卡的 NewLevel 扩展；房租 0.8.2 通过可选 load_after 排在人才市场之后，使房租克隆也继承持物保存钩子。人才市场本身不依赖房租或自由搬运，服务未启用时调用方必须处理 null。员工寻路使用原生地图图结构，重建图时暂时排除员工动态碰撞，墙和设备碰撞规则保持原生行为。

人才市场自己的存档数据 `Save.levelData.ftc_talent_market` 已升级为 `TalentRules.VERSION = 2`；这与 Mod 清单仍使用的 `schema_version: 1` 无关。员工结构示例：

```json
{
  "id": "tm_73021_3_0_0",
  "name": "林小满",
  "role": "employee",
  "stars": 4,
  "skill_slots": ["stock_advanced", "trash_advanced", "aura", "clumsy"],
  "wage": 214,
  "enabled": true,
  "avatar": 0,
  "skin": 1,
  "fashion": {"Body": 0}
}
```

`skill_slots` 固定四个字符串，空槽为 `""`；每槽独立抽取空槽／普通／高级的概率为 50%／45%／5%。同一员工不能拥有重复技能，同系高级技能替换低级技能，两者不能共存。1.1.1 调试版只启用丢垃圾和高级丢垃圾；其他技能原始配置保存在 stored_slots 中，运行及显示通过 slots 过滤。新候选不生成旧四维 `skills`。v1 存档迁移保留原始字段作兼容数据，原岗位映射为相应主动技能、`role` 统一改为 `employee`；员工 ID、姓名、原合同基薪、出勤、外观、计薪标记和物品快照均保留，逻辑不得继续读取旧 `skills` 决定行为。`Rules.MAX_STAFF = 4`，候选仍为 5 人；超额旧合同按原顺序前四个保存在 `staff`，其余完整保存在 `staff_archive`。归档按员工 ID 去重，不自动补位、不生成实体、不占名额、不参与新一天计薪，也不产生离职金；已经开店的 `shift.ids/wages/amount` 保持原值。重复迁移和读档不能复制归档合同。

`stars` 为 1～6，对应精确整数权重 `750/200/30/10/8/2`（总计 1000）、颜色白／蓝／粉／紫／金／彩。`Rules.duration_star(stars)` 返回 `2.5/2/1.75/1.5/1.25/0.5`，作为原生动作耗时的倍率；运行时再乘自身被动耗时倍率及附近最强其他员工光环，移动速度只由移动被动决定。`Rules.wage(profile)` 或 `Rules.wage(stars, slots)` 计算新合同参考基薪；正数 `person.wage` 在迁移和读档时保持，不写回每日涨幅。`market.daily_wage(person)` 在房租局用基础租金曲线相对首日的倍率，在正式关卡用 `1 + 0.5 * (day - 1)`，乘基薪并 `ceil`；免租和租金折扣不影响该倍率。开店保存 `shift = {day, ids, wages: {employee_id: daily_wage}, amount}`，同一天重复开店、查看或读档不得重算该班次；历史基薪不能日复利。

`fire(id)` 仅准备期有效，离职金为员工当日 `daily_wage(person)`，钱不足时不扣款也不删合同；成功即时支付并累加 `state.severance_spent`，次日清零。日终把工资与已付离职金合记到原生 `Cost_Staff/TODAY`，用 `TalentWagesRecorded` 防重复记账，不能再扣一遍离职金。人才刷新费用独立记录在 `refresh_spent/Cost_Items`。

`Rules.candidates(seed, day, catalog = [], refresh_index = 0)` 返回五位候选，种子、日期和刷新索引共同决定稳定名单与 ID。头像目录仍支持 `{avatar, skins, fashion}`，`appearance()`、`apply_appearance()`、`appearance_key()`、`FASHION_PARTS` 和 `OUTFIT_ANIMATION_NAMES` 接口保留。`Rules.for_day(state, day, catalog)` 返回新状态字典，日期变化才把 `refresh_index` 归零并生成当日五人，保留在职合同与库存；同日读档不得清除刷新索引。`Rules.refresh_cost(n)`（别名 `refresh_price(n)`）按此前当天刷新次数计算 `100×2^n`，上限 1,000,000,000；`refresh_candidates()` 即时支付、保存新名单与计次，晚间不得再次扣同一费用。

技能定义位于 `Skills/SkillCatalog.gd`：`get_skill(id)` 返回名称、`kind`、`tier`、说明、能力与修正值；`kind` 为 `active`、`passive` 或 `debuff`，界面与文档将后者称为“被动减益”。`slots(profile)` 总是返回四槽；`has_skill(profile, id)` 包含高级对普通的继承；`capabilities(profile)` 返回布尔能力集合，`modifiers(profile)` 返回纯被动因子，不包含星级或其他员工光环。

主动 ID 为 `cashier/cashier_advanced`、`restock_cups`、`clean`（暂停）、`repair`、`stock_basic/stock_advanced`、`trash_basic/trash_advanced`。普通整理只授予 `stock_open_boxes`；高级额外授予 `move_packages/open_packages`。普通丢垃圾为 `empty_bins`，阈值 `trash_fill_ratio = 0.5`；“高级丢垃圾”还授予 `clear_waste/flatten_empty_packages`。补杯不能绕过运输箱的高级开箱权限；补杯和空箱／废包装处理仍使用真实库存和容量。

被动 ID 为 `efficiency/efficiency_plus`（耗时 0.85/0.7）、`move_speed/move_speed_plus`（移速 1.15/1.3）、`aura/aura_plus`（180/240 像素内其他员工耗时 0.92/0.85）；`clumsy` 为被动减益，耗时 1.3、移速 0.9。光环取最强邻居、不会递归叠加，离开范围或停止出勤即失效。只有被动的员工不因此获得主动工作权限。

模块分工：`TalentRules.gd` 管概率、生成、工资、刷新与迁移；`Skills/` 管技能目录及能力；`AI/SkillScheduler.gd` 统一选择并独占执行任务；`Actors/` 管实体、移动、进度与被动；`Roles/`、`Helpers/` 管原生交互、物资和资源锁；`UI/TalentMarketPanel.gd` 与 `Visuals/PortraitFactory.gd` 独立负责市场和真实形象。`TalentMarket.gd` 集成管理、存档和原生费用结算。扩展任务应先检查技能权限，再锁定资源；取消／保存时归还实际物品，不得直接改杯值或复制库存。

房租 0.9.0 的玩家入口仅在真实 Home 可用，`can_enter_from_home()` 可查询当前是否符合条件；创建、继续按钮和 F4 均再次校验场景与玩家归属。内部 `start_run(settings)` 与 `_continue_run()` 保留编程调用兼容。角色、皮肤、衣装和家居加成使用原生流程。每日礼物的 `remaining_rewards()` 包含正在展示但尚未接受的一份；原生 `cur_Gift` 在展示时扣减，因此其他模块不得拿它覆盖房租剩余权益。房租保底一份，原生声望与家居增加的礼物保留到全部选完。

房租的 `RentSaveData.gd` 仅在离线单机、正式的 `Feed The Cups Rent Mode` 用户目录生效：从相邻 `Feed The Cups/<当前 SdkManager.user_id，或 default>/saves/<dataSavedName>.sav` 读取同账号正常档，不扫描其他账号，不把 QA 目录接到真实存档。`dataSYNC()` 在原生字段进入运行状态前导入共享之家，`_saveLogic()` 覆盖原生镜子、衣柜和日终保存出口。首次同步以正常档的家和绿钞为准，旧房租绿钞不相加；首次变更前备份正常档与房租档原文件到当前房租组 `ftc_mods/ftc.rent_mode/home_sync_backups/<账号>/`。

`Sync/HomeSyncRules.gd` 限定共享 `Game.HomeUpdate/HomeDevList/EquipDic/player_1P_ID/player_2P_ID/JoinPlayer/cur_EquipList/AchievementReward_Array/Achievement_Array`、绿钞的 `HMK/cur_HOMEMONEY/cur_money_home`，以及 `Statistics.Character` 中各角色的 `EXP` 叶。已领取的成就记录用于保留家居升级资格、角色解锁和防止重复领取绿钞；角色经验取两边较高值，其余角色统计仍独立。皮肤和服装库存由同账号的原生 Steam 库存 `SdkManager.equip_dic` 提供，不复制库存、不授予未拥有物品。禁止把整个 `Game`、`Statistics` 或 `Level` 区域拷到正常档；房租天数、黄币、设备库存、员工、正常关卡进度、随机状态与营业资金校验字段均保持各自存档。

`Sync/HomeSync.gd` 使用共享快照基线做三方合并：绿钞只应用本地相对基线的差额，穿搭按改动的叶合并，保留正常档最新的其他字段与未知区段。房租存档的 `FtcHomeSync` 区段保存待提交记录，正常档保存事务回执，写入中断后重试不会重复加钱或扣钱。缺失或不可读的同账号正常档不创建、不覆盖，房租本地保存照常进行。其他模块应让原生保存出口完成事务，不要直接修改同步基线、事务标记或跨目录写存档。

## 声明式场景与脚本扩展

resources 默认映射为 `res://ftc_mods/<id>/<模块内相对路径>`，所以代码必须使用该命名空间。不要引用旧的 mods/rent_mode 或 mods/single_player_trainer。

`script_extensions` 的每项含 scene（原场景资源路径）、base_script（原脚本路径）、script（本模块脚本相对路径）。脚本第一行必须 `extends "原脚本路径"`，覆盖方法按需要调用 `.原方法()`。加载器在构建缓存时重写继承链，接到核心兼容层或前一个 Mod 上，再替换场景的脚本引用。若同一脚本用于多个场景，各场景的继承链必须一致；不兼容链会拒绝启动。

`scene_clones` 每项含 source、destination、base_script、script。destination 需位于本 Mod 资源命名空间，或 `res://TscnAndGd/Main/Level/<id>.名字.tscn`。自定义关卡的 TSCN 值填 `<id>.名字`，因为原版加载器在 Main/Level 下查找。第三方 Mod 不得占用另一个模块的场景名称。

克隆以当前 source 场景为基础，保留先加载模块已经添加的脚本扩展；克隆脚本的第一行也必须继承所声明的 base_script，构建时会接在源场景的当前继承链之后。例如源关卡已经由搬运模块扩展，房租克隆脚本就会继承搬运脚本，再继承原版关卡脚本。后续模块仍可通过 script_extensions 继续扩展克隆场景。使用 dependencies 或可选 load_after 确定组合顺序；克隆完成之后才应用到源场景的扩展不会追溯到克隆。一个克隆脚本复用于多个源场景时，这些场景的继承链必须兼容；重复继承自身、缺失脚本引用或不兼容的继承链会拒绝构建。

`levels` 每项含 name（必须以 `<id>.` 开头）、base（原关卡配置名）及 values（覆盖字段）。此配置在原版解密后应用，不需要改动原版加密 cfg。复杂玩法仍可扩展 ConfigBridge；一般注册接口已足够。

`text_patches` 每项为 resource、find、replace、count（默认 1），要求匹配次数精确。`animation_aliases` 含 resource、from、to，用于新增原有动画的别名。冲突或匹配次数变化时拒绝构建，避免静默覆盖其他 Mod。尽量优先公共 API，其次脚本扩展，最后才使用文本替换。

## 缓存、兼容与命令行

加载器核验原版 EXE/PCK 指纹，组合已启用 Mod 并流式生成一个运行包；不会修改原版文件。模块变化后才重建；普通启动复用缓存。运行包需要约 329 MiB 本地空间，最近两套正式缓存、一套测试缓存会保留；运行中被锁定的缓存保留到以后再清理。

```
杯杯倒满Mod加载器.exe --list --profile both
杯杯倒满Mod加载器.exe --build --profile both
杯杯倒满Mod加载器.exe --launch --profile both
杯杯倒满Mod加载器.exe --install "Example.ftcmod"
杯杯倒满Mod加载器.exe --export example.hello --out "Example.ftcmod"
```

配置包括 default、both、rent、rent_only、trainer、furniture、talent、talent_rent、talent_all；default 保存玩家勾选，talent_all 启用全部四个模块。清空勾选得到无玩法 Mod 的独立测试空间；“启动原版”直接运行原 EXE，使用原版存档。`--qa` 仅用于测试构建，存档组另加 QA 后缀。更新游戏版本时先更新适配层和测试，不能简单删除指纹检查。
